# Structure

## Series Skeleton

固定顺序是：`小白痛点 -> 专家说明项目方案 -> 真实结果 -> 优势亮点 -> 可信信号 -> 小白追问与交付`。角色功能固定，项目内容可换。小白只负责开头替观众说出痛点和全片唯一一次追问；专家出现后接管后续说明，不做来回多轮问答。

本变体把“真实结果/优势亮点”落实为两个独立录屏状态：GitHub 浏览录屏证明项目身份与公开说明，WorkBuddy 使用录屏证明从输入到产物预览的真实操作链。短版尽早进入证据；完整 45 秒版允许先用人物把问题和能力范围讲清，再进入录屏，但 GitHub 不晚于第 20 秒、WorkBuddy 不晚于第 35 秒，且不能用截图动画替代。

1. **小白具体痛点**：第 0 帧已经张口，第 0.00 秒已有可听语音，直接说出观众正在承受的耗时、麻烦、质量压力或选择困难；不要求先展示失败画面。禁止吸气、表情准备、标题卡或静音垫在第一句话之前。目标 1.5–2.0 秒，句子短到能带着情绪一口说完。
2. **专家直说解决方案**：硬切专家，用 1.0–1.5 秒明确说"正好有个开源项目"，说清它解决什么痛点、用什么方式解决。口播不要求说具体项目名，官方仓库 / README / Demo 画面负责建立项目身份。
3. **真实结果**：最迟第 5 秒完整展示官方 Demo、输出图或前后对比，先让观众看见项目真正能交付什么，再解释机制。
4. **优势亮点**：从 `advantage_points` 选择一至三个最能击中观众的点（12 秒档一至两个），每组 1.6–2.4 秒。每个点都按"痛点 -> 具体方案 -> 可见结果"说清楚，再用对应官方证据支撑；不讲与解决痛点无关的背景信息。
5. **可信信号**：用一次清晰的 Stars、Forks、更新时间、许可证或官方活跃度画面增强信任。数字只出现一次，必须带采集时间，不堆砌元数据。
6. **问答与交付**：小白追问一个观众最关心的问题，专家立刻用优势和结果回答，并完成真实交付。不使用"但是 / 不过"式转折，不用泛化关注 CTA。

## Self-Media Pace Contract

- 默认成片 18 秒（`standard_18s`），可压缩到 12 秒、扩展到 25 秒，或选择 `complete_45s` 做 40–50 秒完整讲解。不用慢语速、表情停顿或无声录屏填时长。
- 开头的"小白痛点 + 专家方案"必须在 3.5 秒内完成，真实结果随即在第 5 秒前完整出现。
- 中文口播目标约 5.5–7 个可听汉字每秒。每条镜头的台词字数在写稿时就按镜头时长预算好（字数 ≈ 每秒字数 × 镜头秒数），H3 原生速度直接可承载；单镜头装不下就按语义拆成新镜头，不做后期加速。
- 口播内部不保留超过 0.35 秒的非语义停顿；相邻信息拍之间通常只留 0.04–0.16 秒切口。
- 每 0.6–1.2 秒至少出现一种有效变化：新结论、新动作、新结果、构图变化、证据切换、可信信号落版或关键词强调。
- 情绪必须服务角色：小白是真实受挫后的急切提问，专家是拿到证据后的笃定推进；两者都不能使用客服腔、播音腔或慢速数字人口播腔。

## Timing Modes

| 时长档 | 总时长 | 汉字数（实测前） | 用法 |
| --- | ---: | ---: | --- |
| compact_12s | 12s | 55–78 | 只讲一个亮点，结果证据前置 |
| standard_18s（默认） | 18s | 85–115 | 两至三个亮点 + 一次追问 |
| extended_25s | 25s | 120–165 | 三个亮点 + 更完整机制说明 |
| complete_45s | 40–50s | 190–280 | 痛点、定位、覆盖范围、真实录屏、风险边界、追问与交付完整闭环 |

短版不得把真实结果推迟到第 5 秒之后；`complete_45s` 先在前 20 秒内完成项目定位并进入 GitHub 证据，WorkBuddy 在第 35 秒前出现。只有完整讲解确实包含痛点、定位、范围、结果、边界和交付闭环时，才允许 40–50 秒。实测时长高于目标时，先删铺垫、同义反复和主语，再重新生成原声，不靠长停顿填满镜头。

## Hard Gates

- 第 0.00 秒必须有小白可听语音；"痛点 + 专家方案"在 3.5 秒内完成。
- 真实官方结果最迟第 5 秒完整可读；若前 5 秒只有观点没有证据，结构不通过。
- 短版规划 6–9 个视觉状态变化；`complete_45s` 规划 8–12 个，但每个变化必须对应新结论、证据切换、局部推近、风险边界或交付动作，不靠无意义转场凑数。
- 12 秒版 55–78 个汉字；18 秒版 85–115 字；25 秒版 120–165 字；完整 45 秒版 190–280 字。实测时长高于表格时，先删铺垫再重新生成原声，不做角色差异化加速。
- 结尾不能回到小白惊讶、点头或专家摆姿势，必须由专家完成总结、清单、公式、操作动作或下一步承诺中的一种；短版不超过 30 秒，完整 45 秒版不超过 50 秒。

## External-constraint project branch

当项目需要遵守某种外部约束时，沿用以下通用节拍：

1. 小白零秒提出本期观众的具体痛点和约束：`{project_pain}` + `{external_constraint}`。
2. 专家立即说明"这个开源项目"以及它如何解决该痛点：`{core_capability}`。
3. 先切官方仓库、Demo 或结果素材，让观众看到项目身份和真实产出，再用一次小白追问确认最关键的约束是否保留。
4. 专家用短句回答本期证据能支持的具体动作、结果和交付方式，最后落到可核验的信号 `{trust_evidence}`。

本段只定义问答与证据顺序，不预设行业、项目类型、媒介、文件格式或编辑能力。真实素材采用一次滑入或跳切后稳定停留，禁止连续小碎步位移和抖动缩放。

## Fast audio-first H3 dialogue variant

当目标是短视频快节奏时，将全片拆成四个短对话拍：小白痛点、专家说明开源项目方案、小白追问、专家一句结果。每拍先生成一条角色音频，再用对应参考板生成一条完整 H3 视频（`minimax_h3_lightx2v_v5`）；每拍从第一帧开口，镜头之间原速硬切。总时长控制在约 12–18 秒，不用长句、慢停顿或后期差异化加速制造速度感。真实证据按真实抓取优先路线取材：真实 GitHub 页面截图与滚动录屏优先，其次 api.github.com 官方原始素材，本地合成只在确实无法抓取时兜底；只有明确选择 H3 参考板时，才作为单图单音频的参考输入进入人物动作。
