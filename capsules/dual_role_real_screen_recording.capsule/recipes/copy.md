# Copy

## Voice Contract

小白负责替观众快速说出"我卡在哪"，专家负责用一句"正好有个开源项目"接管视频并连续给出方案和证据。两者都说短句、口语句，不用演讲腔，也不做多轮往返问答。

- 小白：具体、受挫、略急，像问题已经反复发生；一口说完，问题句不超过约 16 个汉字，不故意装笨。
- 专家：开口即方案，短、稳、笃定；第一句不超过约 15 个汉字，随后连续推进证据，不居高临下，不用羞辱式纠错。
- 每句尽量只承担一个信息动作。不要用长串形容词、同义反复或制作术语。
- 专家的每个收益点都必须有对应官方画面直接支持；证明不了的效果词、绝对化结论和数据不要写。

## Project Pain And Highlights

- 第一句先说观众正在承受的痛点，不要求先展示"失败结果"；画面可以同步展示问题场景、待处理对象或压力来源。
- 专家随后直接说"这个开源项目"能解决什么问题、采用什么方案；具体项目名不是必需的口播信息，由官方仓库 / README / Demo 画面建立身份即可。
- 后续每个亮点都必须同时回答三件事：解决哪个痛点、项目具体怎么做、观众能看到什么结果。只保留最有感知的一至三个点：12 秒档一至两个，18/25 秒档两至三个。
- Stars、Forks、更新时间、许可证等只作为可信信号，不能代替项目优势；每项数据必须有官方来源和采集时间。
- 句子直接陈述方案和收益，不使用"但是 / 不过"制造反转，不讲与痛点无关的背景、安装过程或泛化宣传语。
- 当能力覆盖多个发布渠道时，优先说“全平台”或“哪个平台”，再列出观众真正关心的风险类别；不要为了显得全面而逐一念平台名。涉及站外引流时，明确写成“检查/提示站外引流风险”，不能写成引导观众绕过平台规则。

## Episode Slots

写稿前先填七个槽位，再写口播：`project_pain`、`core_capability`、`advantage_points`、`result_evidence`、`trust_evidence`、`mechanism_steps`（可选）、`delivery`。不把具体项目名或输出格式写入可复用话术。

写稿时按下列功能句推进，不把括号内的制作说明直接上屏：

1. 小白用一句短促问题说出项目痛点。
2. 专家用一句短句说明"正好有个开源项目"和人话用途。
3. 真实结果与优势亮点按"痛点 -> 具体方案 -> 可见结果"推进，句式保持平行，每句以动作词开头。
4. 小白一次追问，专家用结果回答，并落到可带走的规则、清单或交付动作。

禁止写法：多轮往返问答、角色互相确认、解释为什么要解释、用"首先/其次/最后"拖慢节奏。需要补充的信息全部交给专家连续讲透。

## Hook And Packaging

- 每期先写 3 个开头候选：痛点直给、耗时反差、结果反差。选择能配合问题场景或压力来源画面的版本。
- 标题、封面、首帧和第一句必须围绕同一 `project_pain` 或 `core_capability`，不要分别追不同热点词。
- 封面负责提出可感知问题，标题负责说明要解决的对象；两者不完全重复。
- 对观众可见的文字中不得出现"六段结构、证据序列、钩子设计"等生产说明。
- 本胶囊默认不烧录连续口播字幕。可以使用少量板书式关键词或实拍重点标记，但它们是独立的信息卡，不是逐字字幕：一张卡只表达一个结论，不能把同一句口播完整重复两遍，也不能与 H3 画面内文字叠成两层。关键词卡应优先使用高对比大字，在 1080×1920 画布上默认不低于 46px，并避开人物嘴部和实拍关键事实区。

## Delivery

`delivery` 必须是镜头里能发生的动作，例如专家递出一页总结、画面保存一张对照、或明确展示下一步入口。只说"学会了吗""关注我"或留下惊讶表情不算交付。

## Project Explainer Copy

- 小白第 0.00 秒直接说具体痛点。专家第一段必须自然说出"正好有个开源项目"和一句人话用途，不要求口播具体项目名，画面用官方项目素材对应跟上。
- 项目口播顺序为：小白痛点、项目解决方案、真实结果、优势亮点、可信信号、小白追问、专家回答与交付。避免安装教程式逐步操作。
- 允许一次短促的"小白追问 -> 专家回答"。追问必须替观众问结果、用法或是否能直接交付，不能为了表演而复述上一句。
- Stars、Forks、更新日期和许可证必须来自官方页面或 API，并在证据清单记录采集时间。画面可用"1.2k+"等不夸大的约数，口播不必强塞数字。
- 不把 README 的自我评价改写成客观排名，不用"最好、第一、全网唯一、完全可编辑"等无法独立证明的词。
- 不强制讲项目缺点或能力边界。除非事实准确性或合规需要，不在短视频中加入与主线无关的限制说明；全片避免"但是 / 不过"式转折。
- 优势表达用具体动作和可见结果，不写"赋能、重构、闭环、生态、颠覆、降维"等 AI 味或宣传腔词汇。

### Project-specific constraint branch

- 当项目需要遵守某种外部约束时，小白直接说出本期观众的具体痛点和约束，不预设行业、媒介、文件格式或交付物。
- 专家紧接着说清楚"这个开源项目"能用 `{core_capability}` 解决 `{project_pain}`；具体项目名留在输入元数据和官方画面中，不强制进入口播。
- 追问只保留一个真实疑问，例如"那 `{external_constraint}` 也能满足吗？"；专家回答落到本期 `result_evidence` 中可见的动作和结果。
- 能力表述必须严格跟随官方证据，不把某一期的格式、编辑能力或输出数量写成胶囊默认承诺。
- 真实素材段的动效用整段滑入、跳切、定格和分段切换；禁止连续微缩放、连续小步平移或抖动式镜头。
- 需要更强自媒体节奏时，允许小白和专家各自短句接话两次：每句只说一个动作，专家不要一口塞完机制、格式和数据；把信息拆成"提出痛点 -> 说明方案 -> 追问 -> 一句结果"。
- 音频优先使用短句和明确情绪表达；若台词超过单镜头可承载长度，应先按语义拆成新的音频与 H3 对话镜头，不用后期加速或静音画面填时长。
