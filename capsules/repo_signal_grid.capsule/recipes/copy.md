# Copy

## wechat_social_value_gate

- Before writing a WeChat Channels title or body copy, verify the angle has hard_value, distinctive_view, or unexpected_use.
- Prefer user value and a specific point of view over generic interaction bait.
- Keep this gate internal; do not print method labels in viewer-facing copy.

## viewer_value_modules

- 写底部文案前先把仓库拆成 3-5 个 viewer_value_modules；每个模块必须记录 `source_facts` 和 `viewer_values`。
- `source_facts` 只写能在原仓库 README、示例、脚本、配置、产物图、demo 或本地实测里找到的事实；不从通用想象里补功能。
- `viewer_values` 是给观众看的句子，不是制作清单。每句话都必须回答用户为什么在意：省了什么动作、降低什么返工、拿到什么结果、判断什么边界，或凭什么值得收藏。
- 公开视频底部 4-5 行必须来自这些 `viewer_values`；不能先写功能清单，再临时润色成价值句。
- 不能把制作检查步骤原样写给观众；应把内部 QA 动作翻译成由本期证据支持的用户结果、使用条件或交付边界。
- 少堆否定词。优先用正向配方写清楚：具体省事物、仓库事实锚点、交付质感、使用边界。

## repo_topic_selection

这一节是 repo/tool/Skill 选题和文案的权威决策层。后文的标题模板、底部卡路由和平台文案都必须服从本节；出现冲突时，以本节的选题结论、事实边界和主公式为准。

### 选题准入

- 不要拿到一个 repo 就直接写标题。先确认它服务的明确人群、高频任务、可验证结果、独特机制、转发对象和使用边界。
- Skills 推荐的核心不是“推荐多少个”，而是“哪类人用哪个 Skill，解决什么高频任务，结果发生什么变化”。内部总公式为：`明确身份 + 高频任务 + 实测筛选 + 可量化结果`。
- 选题至少要能回答：给谁用、解决什么任务、相比现有流程少花什么时间/返工或避免什么风险、是否有真实测试或可见证据、什么情况下不适合。
- 不优先制作只有项目发布消息、宽泛作者观点、stars/Skill 数量罗列、宏大未来叙事、无地址/演示/行动建议的工具推荐，以及只有“神级、封神、王炸、效率起飞”却没有硬证据的题。
- 项目集合不能用数量充当价值。先归纳共同工作流，再选择 3-5 个代表 Skill、模块、产物或实测结果证明它。

### 六维选题评分卡

每项 0-2 分，先评分再进入标题生成：

1. `task_specificity`：是否能说清哪类人面对哪个高频任务；“AI 用户提高效率”计 0 分。
2. `hard_detail`：是否有身份、资源名、数字、时点、动作或结果；至少两类硬细节才计 2 分。
3. `result_proof`：是否有 demo、输出物、before/after、本地实测、统一横评或真实使用者。
4. `forward_receiver`：是否能明确说出观众会转给哪类同事、朋友、负责人或从业者。
5. `open_judgment`：是否存在值不值得装、能否替代、适合谁、结果够不够用等真实判断缺口。
6. `fact_safety`：是否能回到 README、源码、配置、官方页面、原话、演示或本地实测。

评分解释：9-12 分可优先制作；7-8 分先补证据或收窄角度；0-6 分换项目或换角度。`fact_safety=0` 时无论总分多少都不能进入 approved release。

### repo/Skill 六类主公式

每条内容只选一个 `primary_topic_formula`，必要时最多再选一个副公式。不要把人物冲突、道德反噬或身份站队硬套到普通仓库。

1. `hidden_resource` 隐藏资源/直接福利：`做【具体任务】的注意：【可信作者或团队】把【稀缺工作流/资源】开源了，它能完成【具体结果】。` 必须有原始仓库、作者或团队身份、明确资源、任务收益和适用边界。
2. `result_proof` 结果证明/前后对照：`【真实使用者】用【项目】把【原始状态】变成【可见结果】，关键变化是【可核验数字或步骤】。` 必须展示统一输入、输出物、before/after、耗时、返工量或其他真实结果，不能只报参数。
3. `tested_comparison` 同类横评/淘汰结果：`实测【数量】个解决【同一任务】的工具，真正能帮【明确人群】减少【时间/返工/风险】的只有【数量】个。` 测试数量、任务、标准和淘汰结果必须来自真实统一测试。
4. `cognitive_reversal` 认知翻转/隐藏变量：`大家都在看【显眼变量】，这个项目真正补上的是【被忽略的工程步骤】，因此能拿到【具体结果】。` 隐藏变量必须具体、可解释并有实例，不能用另一个抽象名词替换原抽象名词。
5. `risk_warning` 风险警报/可规避损失：`做【普通动作】时最容易丢掉【具体结果或资产】，这个项目用【机制】提前发现或避免【风险】。` 必须写清版本、条件、影响和规避办法，不能把传闻写成事实或只制造恐慌。
6. `workflow_bundle` 完整工作流组合：`从【输入】到【最终交付物】，这套 Skills 把【3-5 个连续任务】接成一条可执行流程。` 必须展示代表 Skill/模块、交接关系和最终产物；数量只能做 proof。

### 标题候选记录与选择

- 仍然生成至少 12 个标题候选，但所有候选必须围绕已选主公式；不要为了凑类型生成核心判断相同的同义句。
- 每个候选的内部记录必须包含：`topic_formula`、`target_user`、`specific_task`、`hard_detail`、`evidence_source`、`forward_receiver`、`open_question`、`risk_boundary`。
- 每个候选按主体前置、任务具体、硬细节、可见证据、熟人转发、真实判断缺口、首屏可证明、事实安全八项评分。
- 最终标题必须同时通过：主体在前 12 个字内或第一阅读单元出现；至少一个不可替代硬细节；去掉“开源、AI、神器、必装”仍成立；换另一个 repo 后不成立；观众能自然复述给一个具体的人；首屏素材可以立即证明。

### 判断—证据—缺口

- 强文案的最小推进单位是：`用户判断或任务身份 -> 项目动作与硬证据 -> 使用结果、边界或未闭合问题`。
- 第一部分先替目标用户完成一个有用判断，不从“今天介绍一个项目”或 README 背景开始。
- 第二部分必须出现不可忽略的证据：资源名、作者身份、真实动作、数字、demo、输出物、before/after 或本地实测。
- 第三部分留下真实使用决策：值不值得装、能不能替代、适合哪类任务、结果是否够用、哪里仍需人工复核。问题必须有两种以上合理答案，不能做生硬互动诱导。
- 4-5 页共同完成整条判断链；每页仍保留 4-5 行完整、通顺、可独立读懂的底部事实链，并且每页只推进一个主要判断。

### 六道质量门

1. `evidence_gate`：核心主张是否有 README、源码、配置、官方页面、原话、demo、输出物或本地实测。
2. `human_benefit_gate`：数字和机制是否已翻译成时间、钱、返工、风险、工作结果或身份影响。
3. `cognitive_load_gate`：单页是否只推进一个主判断，是否避免同时堆叠过多专有名词、数字和主冲突。
4. `forward_receiver_gate`：是否能明确说出这条内容会被转给谁，以及转发者想补哪句话。
5. `interaction_quality_gate`：评论缺口是否来自真实取舍、资源需求或经验补充；如果主要会引来对夸张标题和错误事实的嘲讽，必须重写。
6. `compliance_gate`：性能、替代、开源、免费、风险、伤害和权威原话等主张是否准确、可追溯并保留必要边界。

## user_problem_use_mechanism_formula

这一节把“用户一眼看出有什么用”固化为 repo/tool/Skill 文案的通用 SSOT。它补充前面的六类选题公式：选题公式决定从哪个角度讲，这里的公式负责把角度翻译成用户能立即理解的标题、发布文案和核心特点。公式名只用于 internal/planning，不得出现在公开视频、封面、底部卡、字幕或平台正文。

### user_value_translation_card

写标题前必须先完成一张内部 `user_value_translation_card`：

- `primary_user`：最可能实际使用或转发的人，不写“所有 AI 用户”。
- `concrete_moment`：用户在什么具体时刻遇到问题，必须能拍成画面。
- `current_alternative`：没有这个项目时，用户现在怎样完成任务。
- `friction_or_cost`：当前路径具体多做什么、容易返工什么、丢什么或无法确认什么。
- `project_specific_action`：这个项目真正多做的动作，使用口语化具体动词。
- `usable_result`：用户最后拿到的文件、判断、修改、证据、流程或可执行下一步。
- `unique_mechanism`：它区别于同类的机制、格式、交互、资源或工作流。
- `proof`：README、源码、配置、demo、产物、数字或本地实测。
- `boundary`：需要什么前提、仍要谁复核、哪里不适合。
- `one_sentence_usefulness`：一句话说明给谁、解决什么具体摩擦、为什么非它不可。

如果 `one_sentence_usefulness` 换成另一个 repo 仍成立，先补查项目事实或换角度，不进入标题生成。

### 三条文案公式

1. `标题 = 用户可自认的具体摩擦/场景 + 项目专属动作 + 可用结果`
   - 第一阅读单元先让用户认出自己的任务、麻烦或想拿到的结果。
   - 后半句使用项目专属动作或机制，告诉用户它怎样改变现有路径。
   - 不强迫每条都写成抱怨句；明确愿望、输入物或交付目标也可以，但必须让用途一眼可见。
2. `发布文案 = 当前替代/成本 + 项目如何动作 + 可交付结果 + 适用人群/边界`
   - 前两句优先完成“先说用户为什么需要，再说项目怎么做到”。
   - proof 用来证明动作和结果，不替代用户价值。
   - 不能按 README 顺序罗列功能；每个功能都要说明它改变了哪个用户动作或决策。
3. `核心特点 = 适合谁/什么场景 + 解决什么具体摩擦 + 独特在什么机制`
   - 核心特点是一句使用决策，不是项目分类、技术栈或功能标签。
   - 句子必须同时包含用途和不可替代机制；只写“支持多格式、开源、可扩展、提升效率”视为未完成。
   - 技术术语只有在能解释用户结果时保留，否则改写成输入、动作、输出或边界。

### 四个硬测试

1. `用途测试`：陌生用户只看标题和核心特点，能否回答“我什么时候会用它、它替我做哪一步”。
2. `机制测试`：文案是否出现项目专属动作、格式、交互或工作流，而不是同类工具都能说的能力词。
3. `替换测试`：把项目名换成另一个 repo 后仍成立，必须重写；补入不可替代机制或具体输入输出。
4. `决策测试`：文案是否帮助用户判断要不要试、要准备什么、会拿到什么、哪里仍需人工处理。

### 通用改写形状

- 弱：`支持多种格式，提升工作效率`。强：`只有 {现有材料}？把它变成 {可继续使用的结果}，后续还能 {关键动作}`。
- 弱：`提供浏览器自动化能力`。强：`{重复网页任务} 做完后，继续检查 {结果是否成立}`。
- 弱：`拥有完整设计能力`。强：`{成品} 总是风格打架？先统一 {规则对象}，再生成 {可交付结果}`。
- 弱：`一个高星开源项目`。强：`{具体用户} 在 {具体场景} 少做 {旧动作}，因为它会 {专属动作}`。

公开视频只保留自然人话：先说用户为什么需要，再说项目怎么做到，最后给证据、结果或边界；不得把公式名、槽位名、测试名或制作解释写给观众。
