# Visual

## Rules

- Use the repo_signal_grid renderer's fixed 6:7 light paper-and-orange-grid card system at 1080×1260. Keep titles, screenshots, fact cards, footers, and other meaningful content inside y=30..1230 while extending the same warm-white background, orange grid, and glow continuously through the full canvas. Reduce vertical whitespace and panel heights; do not stretch text or source screenshots.
- Top title uses a 两行大字标题 by default. 第一行写用户价值钩子：这个 repo/Skill 替用户省掉什么、产出什么或解决什么具体卡点。第二行写清是什么 Skill/Skills 类型，例如 `PPT 生成 Skill`、`PDF 处理 Skills`、`Office Skills`、`Agent Skills 工具箱`。不要只把 Skills 类型放进小副标题；小副标题只补 `owner/repo`、stars 或短路径身份。
- Top identity must make the exact subject visible. Prefer `owner/repo` for a repo, or a short Skill path when the video is about one Skill. `REPO SHOWCASE`, `GitHub 项目`, `AI 工具` and similar labels are not enough by themselves.
- If the video actually covers several Skills/modules/tools, keep the title focused on the shared user result and use a dedicated subject list area with `subject_paths`; show 3-5 个代表短路径, not a cramped title or middle-image overlay.
- The top subtitle / identity line must make the exact repo or Skill path readable. For 6:7 renders, keep it around 32-36px, 推荐 34px, and verify the first/contact-sheet frame has clear space between subtitle and the middle panel. The title stack starts below the y=25 identity badge and finishes before the middle panel begins near y=270.
- The fixed palette is a light editorial paper system rather than the original blue-black look: `#FFFDF8` full-canvas warm-white background, translucent orange grid lines from y=0 through y=1260, `#FFFFFF` screenshot surface, `#FFF1E5` fact cards, `#F2D5C2` layered shadows, `#2B1A12` titles, `#493228` body copy, `#806252` secondary copy, and `#F26B2B` as the default accent. Keep the paper-card stacking, orange edge rail, rounded borders, and readable dark-on-light contrast stable across scenes. Do not draw separate blank or solid safe-area bands.
- Middle visuals are a clean evidence/illustration area by default. Do not add a repeated middle title above the image unless a profile or scene explicitly sets `show_middle_title: true`; do not overlay ordinary image labels unless `show_image_labels: true`. Generated visuals are the exception: they must carry a small visible disclosure such as `能力模拟` or `结构示意`, either inside the visual or through an explicitly enabled image label.
- Use a mixed visual contract. Every approved scene image maps to `source_asset_manifest` with an existing local `path`, `reconstructed_card: false`, a concrete provenance class, and a capture/generation method. Browser evidence uses `actual_source: true`; purpose-built simulations and explainers use `actual_source: false`, `synthetic: true`, a visible `disclosure_label`, and source-backed `evidence_basis`.
- An approved 4-5-page release must retain at least one original repository screenshot captured from the actual GitHub repository/README page. A generated hero, simulation, diagram, X screenshot, Reddit screenshot, or external project page cannot satisfy this minimum.
- Before generating anything, audit the repository's own screenshots, README images, demos, output examples, UI, charts, GIF/video, docs, and public discussions. Use strong original material directly. Generate only when the first image or later images do not communicate the project's value clearly at phone size, or when the repository is mainly long-form text and lacks a usable visual explanation.
- Treat any user-provided reference prompt as evidence for transferable visual decisions only. Distill the intent, information hierarchy, editability, readability, and evidence boundaries; do not promote its subject, domain terminology, named nodes, fixed canvas dimensions, exact topology, colors, or export checklist into reusable capsule defaults unless the current repository independently requires them.
- Approved browser evidence types are `browser_evidence_screenshot`, `readme_embedded_image`, `project_discussion_image`, and `external_project_related_image`. Approved generated types are `simulated_project_output` and `explanatory_svg_diagram`; these are explanatory/editorial assets, never source evidence.
- Legacy/diagnostic source asset types: `repository_image`, `documentation_screenshot`, `source_file_screenshot`, `demo_output_screenshot`, `video_or_gif_frame`. They may explain why a project was skipped, reproduce older compatibility runs, or support internal review; they cannot be counted as approved middle visuals.
- Source priority starts with the original repository: `1` actual browser GitHub repo/README key-area screenshots; `4` actual browser screenshots of visible README images or page elements. Then use real public context when it materially helps: `3` representative X or Reddit discussion screenshots when discussion volume is meaningful; `2` actual browser external project/docs/demo/release page screenshots. If these assets still have weak visual expression, add a source-grounded simulation or SVG explainer rather than filling the video with unreadable text screenshots.
- Chinese-facing capture ladder is scene-position aware. Opening image priority is strict: (1) official Chinese rendered README; (2) the same README visibly translated in a real browser with Google Translate; (3) the original rendered README. Later-image priority is: (1) useful image, gallery, GIF, video frame/player state, UI, chart, or result visible inside README/docs; (2) relevant X project-discussion post screenshot; (3) source-grounded editable SVG explainer with visible `结构示意`; (4) Chinese repository/README text captured in the browser; (5) plain-English browser screenshot. A Google-translated item uses `capture_method: actual_browser_google_translated_readme_screenshot` and records `translation_provider: Google Translate`, `translated_from_language`, `machine_translated: true`, and `readme_language_used`; never label it as an official Chinese README.
- Browser evidence rule: `browser_evidence_screenshot` must come from an actual browser-opened GitHub/official/project page. 第一帧优先使用真实浏览器 README/仓库关键区域截图. Use `capture_method: actual_browser_github_repository_page_screenshot` or `capture_method: actual_browser_github_repo_readme_key_area_screenshot`; crop so address bars, URLs, sidebars, browser chrome, QR codes, command blocks, generic file lists, and link prompts stay out of frame. Before capture, name the one README/result/table/UI area that proves the scene, target at least 65% core-region occupancy, and preserve only the nearby headings, legends, labels, or comparisons needed to interpret it. If wider context must remain, record `capture_scope: context_plus_core` plus `core_region_description`, then set the scene to `motion_direction: local_zoom` with `core_focus`. A broad page with no core focus is not approved. 禁止把 Markdown 文本用本地 HTML/PIL/模板重新排版成 README 图片.
- Browser README image rule: if README/docs contains a useful image, open the README/docs page in the browser and screenshot the visible image element with `capture_method: actual_browser_github_readme_image_element_screenshot`. Do not use `downloaded_or_copied_readme_embedded_image` for an approved release.
- Social/project page rule: X search, Reddit threads/search, project discussions, official docs, demos, release pages, or project pages are approved only when captured as real browser screenshots with `actual_browser_x_search_screenshot`, `actual_browser_reddit_discussion_screenshot`, or `actual_browser_project_page_screenshot`. Use social screenshots only when there is enough substantive discussion to show real adoption, disagreement, use cases, or pain points; select a representative view, avoid cherry-picking, and crop personal data, unrelated replies, URLs, and browser chrome.
- README content screenshot note: a real browser README content screenshot can explain a skipped/diagnostic record, but `actual_browser_source_readme_content_screenshot` and local source/Markdown screenshots are forbidden as approved source material.
- Generated output simulation is legacy compatibility only and is outside the new opening/later priority ladders. It can reproduce older runs but must not displace README media, X discussion, SVG, Chinese repository text, or plain-English screenshots in a new run. Existing simulation manifests still require `actual_source: false`, `synthetic: true`, `disclosure_label: 能力模拟`, `evidence_basis`, and `style_basis`.
- SVG explainer rule: when the project is mainly long-form text, create a clear editable SVG that explains one decision path, such as `如何使用`, `适合 / 远离`, `输入 -> 处理 -> 输出`, or `设计思路`. Prefer a path, flow, decision tree, layered architecture, or before/after relationship over a generic card wall. Keep labels short, arrows unambiguous, and the information hierarchy readable at phone size. Match the repository's visual language while keeping the capsule's warm-white/orange frame unchanged. Export a PNG preview for the renderer and retain the editable `.svg`; record `asset_type: explanatory_svg_diagram`, `capture_method: authored_svg_explainer_png_preview`, `disclosure_label: 结构示意`, `evidence_basis`, `style_basis`, and `editable_source_path`.
- Never recreate README text, GitHub chrome, a fake terminal, or a fake source screenshot and call it an original capture. Purpose-built generated visuals must explain capability or structure, must be visibly disclosed, and must not carry `actual_source: true`.
- Fallback order when rich media is weak: preserve at least one real GitHub repo/README screenshot; use strong browser-visible README/result elements; add representative X/Reddit or external project evidence when it exists; then create source-grounded simulated outputs or SVG explainers for the remaining visually weak beats. Ordinary documentation/source/config screenshots and legacy local assets remain diagnostic-only.
- If the audit cannot produce at least one original repository screenshot, fail the approved render. If the screenshot minimum is met but the remaining scenes are visually weak, prefer purposeful generated simulations/explainers over repetitive or unreadable browser text captures.
- Pure background, blank texture, or decorative imagery is not enough middle material unless it is the project's own visible result and contains understandable information.
- Crop or mask visible URLs, domains, browser chrome, QR codes, and link prompts. If a screenshot cannot be cleaned without losing the point, choose another source.
- Let visual motion serve readability. Prefer a tight core-area capture. Use local zoom when context must remain. Use long-axis motion only when the sequence or relationship among multiple regions is itself evidence; never keep the core proof unreadably small just to show the whole page.
